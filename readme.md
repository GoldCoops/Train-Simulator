# Train Simulator

A train network simulator written for COMP2000, it is built with Java 21 and Swing. It generates a random rail network and runs trains across it which move passengers between stations.

## Requirements

- JDK 21 or newer

## Build and run

```
./gradlew run      # launch the application
./gradlew build    # compile and run the tests
./gradlew test     # tests only
./gradlew jar      # runnable jar into build/libs
./gradlew javadoc  # API docs into build/docs/javadoc
```

On Windows use `gradlew.bat` in place of `./gradlew`.

Compiled jar can be run with: 

```
java -jar build/libs/COMP2000-Semester-1-Project-1.0.jar
```

## Using the simulator

From the main menu, choose **Start Simulation**. A random network of connected stations, junctions, and
tracks is generated, and two trains are spawned.

The canvas supports:

- scroll to zoom, click, and drag to pan
- hover over a train, station, or junction to inspect it in the sidebar

The sidebar controls play/pause, a speed multiplier from 0.25x to 8x, resetting to a fresh
network, spawning extra passengers or trains, and fitting the view to the network. Statistics
show elapsed simulated time, active trains, and passengers waiting, onboard and delivered.

## How it works

The simulation runs on a fixed timestep. `SimulationController` drives a Swing timer at roughly
60 frames per second, accumulates real elapsed time (scaled by the speed multiplier) and feeds it
to `Simulation.tick` in fixed 1/60 second steps, so movement is identical regardless of frame
rate. A long stall is clamped rather than applied, so a hitch cannot teleport a train across the
network.

Each tick, every vehicle integrates its speed against the timestep and advances along its route.
On reaching a station it stops, unloads any passengers that have arrived, boards any whose
destination lies ahead on its route, and waits out a dwell period before departing.

When a train finishes its route, the controller picks a new destination for it. Candidates are
ranked by whether the station is starving (unserved for over 60 simulated seconds), then by
passenger demand at the current station, then by passengers waiting at the candidate, then by
how long it has gone unserved, with route length only breaking otherwise equal ties. The
starvation rule is what bounds the worst case rather than just improving the average.

Routing is A\* over the network graph, using straight-line distance as the heuristic and total
track length as the cost. Cost is currently physical distance rather than travel time; swapping
in time only changes what feeds the score, not the algorithm.

Networks are generated by placing stations on a grid, wiring them into a random spanning tree so
everything is reachable, then adding a few extra tracks so more than one route exists between
some pairs. Tracks bend through elbow junctions rather than running diagonally.

## Project layout

```
src/main/java/com/trains/
  App.java          entry point, opens the main menu
  cargo/            Cargo, CargoType, CargoHold and transfers between holds
  network/          Network, Node, Station, PathwaySegment - the graph
  routing/          Router (A*) and the Route it produces
  sim/              Simulation tick loop and CargoSpawner
  ui/               SimulationController (when things happen), SimulationView (drawing),
                    RandomScenario (network generation)
  ui/gui/           Swing menu screens
  utils/            GridPos, Point2D, MathUtils, StationNames, I18N
```


Positions use `GridPos`, a record of non-negative integer coordinates on a fixed grid. Vehicles
track a distance along their current segment and interpolate screen coordinates from it, so
rendering never drives the simulation state.

## Tests

JUnit 5, run with `./gradlew test`. Coverage focuses on the domain layer: cargo holds and
transfers, network construction and connection rules, routing, itineraries, vehicle movement and
cargo spawning. Reports land in `build/reports/tests/test/`.

## CI

- `gradle.yml` builds and tests every push and pull request against `master` and `dev`
- `javadoc.yml` generates API documentation
- `release.yml` builds a runnable jar on a `v*` tag and publishes it as a GitHub release
